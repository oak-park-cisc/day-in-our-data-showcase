# Day in Our Data — AI Judging Panel Rubric

Six AI judge personas each score every submission on a 1–5 scale, then a
separate matchup pass runs head-to-head comparisons. This page describes what
each judge is looking for and how they score it.

These scores are generated by a language model panel. **They decide nothing.**
Awards at Day in Our Data are determined by the participant vote. The panel
runs independently so its ranking can be compared against the crowd's — the
comparison is the point, not the verdict.

## Civic Impact

**Does this project answer a question a real Oak Park resident actually has?**

- **5** — Answers a question residents ask out loud, for a clearly named group of people.
- **4** — Clear civic value; the audience is implied rather than named.
- **3** — Plausibly useful, but the need is assumed rather than shown.
- **2** — Interesting as data work; the civic question is thin.
- **1** — No discernible resident-facing question.

## Data Integrity

**Are sources named and are the limits of the data stated?**

- **5** — Sources are named and caveats or limitations are stated unprompted.
- **4** — Sources are named; limitations are only partially addressed.
- **3** — Sources are identifiable but not clearly stated, and limitations go unmentioned.
- **2** — Sources are vague or implied, with no acknowledgment of gaps.
- **1** — Conclusions are presented with no stated source at all.

## Data Provenance

**Could someone retrace how every number got from the raw data to the finished result?**

Data Integrity asks *where* the data came from; Data Provenance asks *what was
done to it*. Named steps (filtered, joined, aggregated), captured in a script,
notebook, query, or spreadsheet formula, make a result reproducible. Figures a
model generated and pasted in, with no check against the source, do not. A
written list of steps someone took by hand counts as traceable.

- **5** — Every transformation from source to result is described or captured in a rerunnable form; the outputs could be reproduced by someone else.
- **4** — The main transformations are traceable; a minor step is described only loosely.
- **3** — The general method is described, but at least one step that changes the numbers is unexplained.
- **2** — Results are shown with only a vague account of how they were produced.
- **1** — Figures or data appear with no traceable origin, or were generated by a model with no check against the source.

## Usability & Access

**Could a resident who is not technical actually use this?**

- **5** — Usable at a glance; plain language, no special knowledge required.
- **4** — Usable with a little orientation; mostly plain language.
- **3** — Usable, but a resident would need to work at it or ask for help.
- **2** — Understandable mainly to someone already familiar with the data or the tool.
- **1** — Requires technical expertise the intended audience does not have.

## Craft

**Is it finished and working, in whatever form it takes?**

A finished CSV outranks a broken web app.

- **5** — Complete and functioning as presented, with no loose ends.
- **4** — Functions well; small rough edges that do not block use.
- **3** — Mostly works, but a noticeable piece is missing or broken.
- **2** — Partially working; significant parts are incomplete or unreliable.
- **1** — Fragmentary; does not hold together as a finished piece of work.

## Continuation

**Could CISC or Village staff pick this up on Monday?**

- **5** — Documented well enough that staff could hand it off and continue Monday.
- **4** — Mostly documented; a knowledgeable staff member could pick it up with minor digging.
- **3** — Some notes exist, but real effort would be needed to reconstruct intent or method.
- **2** — Little documentation; continuation would mean starting over in most respects.
- **1** — Nothing to continue from.

## What the panel reads

- Each team's written entry: title, starter project, what they built, what it
  solves for, and how they got from the raw data to the result.
- The team's README, when one can be retrieved: from an uploaded zip (the
  Civic Spark export) or the linked GitHub repository. The first 4,000
  characters are read. Civic Spark's unedited placeholder README counts as no
  README, and its shared starter-project card is ignored.
- The names of any uploaded files and the links, as text.

The panel does **not** run apps, open demos, or read code or data files. A
submission without a README is scored on its written entry alone, and the
missing README is not held against it.

## How scoring works

- Code is not required for any category. A cleaned dataset, a printed map, or
  a clearly documented open question can score full marks.
- **AI use is neither rewarded nor penalised.** A traditional project (a
  deterministic script, a standard chart, a plain web page) is judged on
  exactly the same terms as an AI-assisted one.
- Every score must be grounded in evidence drawn from the submission itself.
- The panel is never given team names — submissions reach it under anonymous
  IDs. A team's own README may still mention its name; the panel is told to
  score the work, not the team.
- A judge that cannot produce a valid, evidenced verdict abstains rather than
  guessing.

## How the bracket is decided

After scoring, entries are seeded by mean score and play head-to-head
matchups. Each judge compares the pair twice, with the order swapped; a vote
counts only if it names the same winner both times. The majority of counted
votes wins. Six judges can split 3–3: a tie goes to the entry the Data
Provenance judge chose, and if that judge's vote did not count, to the higher
seed.

## How the vote and the panel combine

They do not. **The participant vote alone decides the winner.** The panel's
scores and bracket are never added to, averaged with, or used to break ties in
the vote. The results page shows the two rankings side by side, with a
correlation between them and each judge's individual agreement with the
crowd, so readers can see where people and machines agreed.
