# Decision log

Decisions taken while building this site that cannot be recovered from the code or
the commit history: what was decided, why, and what it costs if it turns out wrong.
Preserved from the build ledger so the reasoning outlives the process that produced it.

Entries marked **Owner decision** were made by the repo owner. The rest were made
during the build and are open to being revisited.

36 decisions, in the order they were made.

---

**1.** work proceeds on a feature branch rather than a git worktree — the repo is one day old, has no competing work, and a branch gives identical isolation without Windows worktree path juggling. Cost if wrong: none; the branch can become a worktree at any time.

**2.** Conflict A — T10 imports `Pairing` from `judging.bracket` and builds later rounds with it directly; guard the loop on `if not advancing` before pairing. Reason: `type(x)` on a list element is a construct a reviewer would correctly flag, and the empty case is reachable if every pairing is a bye. Cost if wrong: trivial, localised to one loop.

**3.** Conflict B — drop `_codes_never_stored` from `TallyResult`. Reason: the test asserting codes are absent passes on the real structure; a field that exists to look reassuring is noise. The guarantee lives in `tally()` never copying `b.code` into the result. Cost if wrong: none.

**4.** Conflict C — the Netlify build command becomes `rm -rf site/data && cp -r data site/data`. Reason: the plan's form nests `site/data/data` on any re-run, which silently breaks every fetch path. Cost if wrong: none; idempotent either way.

**5.** Conflict D — no `judging/schema/*.json` files. The Pydantic models in `judging/schemas.py` are the schema, and `messages.parse()` enforces them server-side. Reason: duplicating them as hand-maintained JSON Schema gives two sources of truth that will drift. The spec's §3 tree is superseded here. Cost if wrong: if an external consumer ever needs the JSON Schema, it is one `model_json_schema()` call away.

**6.** Task 3 Important #1 (build_rounds crashes on empty/single entry) — FIX, even though the plan's code is what was implemented and run_panel guards with len(seeded) >= 4 so the crash is unreachable today. build_rounds is a public function and the guard lives in a different module; a latent IndexError behind a caller's discipline is a trap for the next caller. Cost if wrong: three lines.

**7.** Task 3 Important #2 (dead `a is None and b is None` guard) — REMOVE it rather than keep it as defence. Verified unreachable: standard seeding pairs sum to size+1, and size is the smallest power of 2 >= n, so n > size/2 and every pair holds at least one real seed. Dead code that looks like an empty-bracket guard is worse than no guard, because it stops the next reader from asking whether the case is handled. Cost if wrong: a real both-None pair would raise instead of being skipped — impossible under the invariant above.

**8.** Task 3 test gap (even-split test would pass with the tie branch deleted) — FIX. My plan wrote that test; the vote order made P-01 both the higher seed and first-counted, so Counter.most_common() insertion order masks the branch. A test that cannot fail is not a test. Cost if wrong: none.

**9.** Task 4-5 Critical (spearman ranks full dicts then subsets to shared keys) — FIX. This is a defect in the PLAN's code, not the implementer's transcription. Confirmed reachable: build_comparison calls spearman(shared, panel_by_id) where panel_by_id can hold keys absent from shared, and the per-persona loop likewise. Non-shared items leave rank gaps that distort the shared items' relative ranks — wrong coefficient, no crash, no failing test. The comparison page exists to display that number. Cost if wrong: none; ranking the intersection is correct under every input.

**10.** Task 4-5 Important (reused code marked `seen` only after a ballot passes all other checks, so "first ballot wins" is really "first VALID ballot wins") — KEEP the behaviour, document and test it. A voter whose first attempt is malformed should not forfeit their vote; burning a code on a rejected ballot punishes a typo. No exploit exists — extra invalid ballots gain nothing, and the code locks on the first valid one. Cost if wrong: a voter could retry after a rejected ballot, which is the intent.

**11.** Task 6-7 Important (craft.md splits "A finished CSV outranks a broken web app." across a hard line wrap) — FIX, but folded into the Task 8-9 dispatch rather than given its own fix round. The text reaching the model is semantically identical (a newline in a prompt is not a difference), no test asserts the string, and the reviewer confirms it renders correctly; the only failure mode is a hypothetical literal grep that does not exist. A dedicated round plus scoped re-review for one newline is not proportionate. Cost if wrong: the string stays wrapped one more task.

This is a third defect in my plan, not a deviation by the implementer, and the brief's own Step 5 smoke test could not pass without fixing it. Cost if wrong: the --mock CLI path is dry-run scaffolding only; no production path touches it.

**24.** JUDGE_MODEL becomes claude-sonnet-5 in BOTH judge.yml and client.py's DEFAULT_MODEL fallback. The owner chose Sonnet 5 after a measured cost comparison (~290 calls for a 20-project event, ~400K in / 120K out: Opus 5 ~$5.00, Sonnet 5 ~$2.00, Haiku 4.5 ~$1.00 per full run). **25.** OpenRouter NOT added. AnthropicJudgeClient uses messages.parse() with Pydantic-enforced structured output; an OpenAI-compatible backend means reimplementing schema validation and retry, a second secret, and a new failure mode — schema-invalid JSON is treated as ABSTENTION by pass1/pass2, so a flakier judge degrades the panel silently rather than erroring. The saving is about one dollar. Batch API (50% off) and prompt caching were also considered and rejected: caching cannot engage at all because the persona prompts are ~330 tokens, below the 512-token minimum cacheable prefix.

**26.** _hash_code's docstring claim — "the code space is 32**10 (~1.13e15) ... so a plain hash is not brute-forceable from data/ballots.json alone" — is FACTUALLY WRONG and must be corrected. 32^10 is 2^50; unsalted SHA-256 over that space runs in ~14.4 hours on a single commodity GPU, and ~14 minutes to the first hit against ~60 published target hashes. The CONCLUSION that the current design is acceptable still stands, but for a different reason the comment does not give: only codes that have ALREADY been spent are published, and tally consumes a code on its first valid ballot, so a recovered hash yields an unusable code. A wrong security guarantee sitting in a public repo is worse than no comment, because the next person to reuse the pattern — on unspent codes — inherits a defence that does not hold. Cost if wrong: none; the comment is the fix.

**27.** ballot hashing STAYS plain SHA-256 — owner's decision, declining the keyed-HMAC upgrade and its fourth secret. The corrected docstring now carries the real reason it is safe.

**28.** both Important findings FIXED rather than parked, despite the reviewer marking them non-blocking. Neither is a judgement call and both are a few lines. (2) _http_get_json puts the raw HTTP response body into the raised error, which main() prints to stderr; on an error from the BALLOT submissions endpoint that body can carry raw voter codes into a public Actions log. GitHub's secret masking does not cover them — the masked value is BALLOT_CODES, not a voter's submitted code field. Cost if wrong: trivial either way.

**35.** **Owner decision.** Ballots never enter the repo. Supersedes #33's premise. The owner made the repo public on 2026-09-24 so Netlify's free plan could deploy it (the free plan cannot deploy a private, org-owned repo). #33 accepted a committed `data/ballots.json` on the grounds that ballot secrecy rests on codes staying on the slips; with the repo public, that file lets any slip-holder read a named voter's picks, and nothing requires it to exist. `sync-submissions.yml` no longer fetches ballots; `tally.yml` reads them from the Netlify Forms API via `fetch_ballots()`, holds them in memory, and commits only `vote.json` and `comparison.json`. `.gitignore` and `tests/test_netlify_config.py` guard against a stray ballot file. **36.** **Owner decision.** Stay on Netlify's free plan, with data read live from GitHub. Free is 300 credits a month at 15 per deploy (about 20 deploys) with a hard pause at the cap, and every bot data commit used to rebuild the site. Now bot commits carry `[skip netlify]` and pages fetch `data/*.json` from `raw.githubusercontent.com`, falling back to the deploy-time snapshot on failure (GitHub allows about 5,000 unauthenticated requests per hour per IP, and a library's wifi is one IP). Moving to Cloudflare Pages or GitHub Pages was rejected nine days before the event: Netlify Forms carries submissions, uploads and ballots with no backend of ours, and replacing it means new vote-handling code on a deadline. The owner's own domain is added as a single DNS-only CNAME; teardown deletes the CNAME before the Netlify site to prevent takeover. Cost if wrong: up to ~5 minutes of display lag behind each data commit.
